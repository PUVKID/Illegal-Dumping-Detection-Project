## LEVEL 1 - Beginner

사진을 준비하다가 멈춘 원인은 과거에 저장한 사진 이름과 다음 준비 코드가 알아보는 이름이 달랐기 때문입니다.

예를 들어 `plitter_47668.jpg`의 47668을 공식 주석의 사진 ID와 대조합니다.

경로에 우연히 들어 있는 숫자를 사진 번호로 추측하지 않습니다.

**13차는 같은 실험을 이어 갈 수 있게 연결하는 복구 도구**이며 새 모델 성능을 측정한 결과가 아닙니다.

| 확인할 일 | 쉬운 예시와 동작 | 남는 자료 |
| --- | --- | --- |
| 사진 번호 찾기 | 마지막 파일명 전체가 plitter 또는 street 접두사·양의 정수·jpg 형식이어야 함 | 공식 ID 대응표 |
| 잘못된 이름 막기 | 0·앞자리 0·jpg.bak·모르는 ID·같은 번호 중복은 거부 | 실패 원인 보존 |
| 원래 동작 지키기 | 복사한 준비 코드의 위치·가져오기·번호 해석·원본 해시 표시 네 곳만 변경 | 원본 계약과 별도 복구 계약 |
| 준비 전후 나누기 | 먼저 코드와 자료를 고정하고, 실제 준비 뒤 파일 목록을 다시 고정 | recovery13.json·prepared.json |
| 같은 작업 이어 가기 | 한 작업만 실행하고 이전 실패와 새 시도를 resume_of로 연결 | 잠금과 작업 이력 |
| 보고서 만들기 | 정상 종료와 선택 가중치·세 고정 테스트·복구 계약 확인 뒤 생성 | 같은 원고 Word·PDF 두 파일 |

대응을 확인한 ID는 과거 1,999개, 5차 3,839개이며 겹치는 642개를 한 번만 세면 합 집합 5,196개입니다. 이는 새 학습 성능이나 새 사진 다운로드 수가 아닙니다. 과거 사진은 다시 JPEG로 저장하고 최대 2,048로 줄인 것이어서 새 공식 원본과 바이트가 같다는 뜻도 아닙니다.

먼저 기존 7차 설치와 보존 사진·공식 주석·완성된 캐시가 있는지 확인한 뒤 아래 공통 검증 안내를 따릅니다.

공개 코드만 내려 받으면 원본과 모델·비공개 실행 계획이 없어 그대로 시작할 수 없습니다. 7차 기준 16 파일은 11개 일치·2개 부재·3개 상이하므로 기준 해시를 새 값으로 바꾸면 안 됩니다.

조회와 보고서 확인은 학습을 시작하지 않습니다.

실제 시작에는 비공개 계획과 독립 검토에서 고정한 expected-canonical이 필요하며 현재 중단한 학습을 이 문서를 보고 재개하지 않습니다.

Windows 검사는 43개를 모았고 Linux 전용 1개는 건너뛰었습니다.

Docker에서는 43개를 통과한 기록이 있습니다.

번호의 모호함·파일 변조·중복 시작·보고서 연결을 검사한 결과이며 실제 GPU 학습이 끝났다는 뜻은 아닙니다.

원래 두 후보의 최대 60·45 epoch와 각각 6시간 계획을 유지하고, 정밀도·재현율 90% 달성은 보장하지 않습니다.

보고서 연결 시험은 합성 자료였으며 실제 개인 최종 보고서를 공개한 것도 아닙니다. 14차의 DMF 문서 롤 백 기능과 이 복구 기능은 구분합니다.

### 현재 공개 사본의 원본 대조

불변 Git blob과 original-baseline의 실제 대조에서 **7차 기준 16 파일은 11개 일치·2개 부재·3개 상이**입니다.

없는 파일은 docs/구현 계획.md와 docs/설계.md이며, 다른 파일은 docs/이전 검증 분석.md·docs/출처와 실험 계약.md·tests/test _worker.py입니다.

상 이 파일을 모두 개 행 차이로 단정하지 않습니다. 10·12차 의존성을 포함한 전체 original-baseline 21 파일은 16개 일치·2개 부재·3개 상이입니다.

아래 보존 전문이나 과거 설명의 “16 중 13”은 이전의 불충분한 대조이며 현재 판정에는 이 재대조를 적용합니다.

원본 baseline과 과거 원문을 고쳐 결과를 맞추지 않습니다.

### 검증과 원문 연결

보존된 13차 설치 폴더를 cwd로 사용해 `python -B -X utf8 -m unittest discover -s tests -v`와 `python -B -X utf8 verify_sources.py`를 실행합니다.

독립 검토에서 별도 보존한 SHA가 있을 때 `verify_sources.py --expected-canonical`의 값으로 지정합니다.

현재 값을 새 원본 기준으로 쓰지 않습니다.

이 문서 편집에서 검사를 새로 실행한 것으로 쓰지 않으며 위 숫자는 보존 검증 기록입니다.

## LEVEL 2 - Explorer

복구의 핵심은 **파일명에서 얻은 ID와 공식 주석의 ID를 연결하고, 그 연결에 사용한 코드까지 고정하는 것**입니다.

과거 생성기는 plitter 접두사를 사용했고 다음 준비 코드는 street 접두사를 찾았습니다.

새 해석기는 경로의 마지막 이름만 완전 매칭하므로 부모 폴더 숫자나 확장자 뒤 글자를 오인하지 않습니다. plitter와 street의 양의 정수 ID만 허용하며 선행 0·중복·공식 주석 간 불일치·모르는 ID는 거부합니다.

| 연결 단계 | 앞 단계에서 받는 것 | 다음 단계에 주는 근거 |
| --- | --- | --- |
| 공식 대응 | 보존 파일명·과거 생성 코드·동일 공식 주석 | 과거 1,999·5차 3,839·중복 642·합집합 5,196 ID |
| 정적 파생 | 보존 7차 준비 코드 | import·ROOT·ID 호출·원본 SHA 표현 네 변화만 있는 실효 코드 |
| 시작 전 동결 | 실효 코드·resolver·공식 입력·캐시·이전 작업 | source_frozen과 복구 계약 |
| 준비 후 동결 | 실제 data_manifest와 원래 준비 계약 | 별도 prepared.json과 prepared 상태 |
| 실행 연결 | 같은 두 후보 계획·원래 worker | 잠금으로 단일 실행, 실패와 resume_of 계보 |
| 보고서 연결 | 정상 완료·선택 가중치·고정 테스트 | 기본 검증 뒤 복구 검증을 더한 Word·PDF |

원래 preparation_sha256은 7차 코드의해 시로 남기고, 실제 실행한 파생 코드와 ID 해석기는 recovery13 계약에 따로 담습니다.

준비 전에는 아직 없는 최종 manifest를 고정했다고 주장하지 않고 실제 준비가 끝나면 두 번째 기록으로 결합합니다.

보고서 연결도 12차 기본 검증을 생략하지 않고 validate_recovery로 코드·입력·계보·준비 manifest를 더 확인합니다.

실패·진행 중 작업은 정상 최종 문서로 만들지 않습니다.

ID 합집합은 공식 대응의 집계입니다.

재인코딩·최대 2,048 축소된 과거 JPEG와 새 원본의 SHA가 같다는 주장이 아닙니다.

완성된 캐시를 크기·MD5·SHA로 확인해 재사용하며 없거나 바뀐 경우 새 다운로드로 우회하지 않습니다.

원래 분할·정규화·검증·테스트 조건과 두 후보의 최대 60·45 epoch, 후보당 6시간을 유지합니다.

조회와 보고서 생성은 학습 기동과 별개이고 시작에는 고정 canonical과 비공개 계획이 필요합니다.

기존 설치에서 아래 공통 검증 명령을 사용합니다.

기록된 검사는 Windows 43개 중 Linux 전용 1개 건너뜀, Docker 43개 통과이며 ID·해시·잠금·계보·보고서의 제어 사례를 확인했습니다.

이것은 GPU 완료나 90% 성능 보장이 아닙니다.

공개 본은 7차 기준 16 파일 중 11개 일치·2개 부재·3개 상이와 대용량 자료·모델·비공개 계획 부재 때문에 완전한 실행 환경이 아닙니다.

원래 baseline을 현재 해시로 바꾸지 않습니다.

로컬 계약은 외부 신원 인증이 아니며 13차에 DMF 병합·롤백을 구현한 것으로 해석하지 않습니다.

### 현재 공개 사본의 원본 대조

불변 Git blob과 original-baseline의 실제 대조에서 **7차 기준 16 파일은 11개 일치·2개 부재·3개 상이**입니다.

원본 baseline과 과거 원문을 고쳐 결과를 맞추지 않습니다.

## LEVEL 3 - Practitioner

재현에는 **기존 7차 동결 설치와 보존된 공식 입력·완성 캐시·모델**이 필요합니다.

공개 저장소 단독 복제 본은 7차 원본 기준 16 파일 중 11개가 일치하고 두 개가 없으며 세 개는 바이트가 다릅니다.

검사 실패를 기준 해시 교체로 우회하지 말고 필요한 보존 원본을 먼저 확인합니다.

아래 검증 명령은 읽기 검사이며 실제 재개를 지시하는 명령은 아닙니다.

| 순서 | 사용자 확인과 처리 | 성공 조건·거부 시 대응 |
| --- | --- | --- |
| 1.<br>소스 확인 | 원본 baseline과 13차 전체 canonical 대조 | import·ROOT·ID 호출·원본 SHA 표현 네 변화 외 차이 거부 |
| 2.<br>입력 확인 | plitter/street 양의 정수 jpg 전체 이름과 공식 주석 대조 | 선행 0·중복·미확인·출처 불일치 거부, 추정 보정 금지 |
| 3.<br>시작 전 | 비공개 재개 계획·외부 동결 expected-canonical 준비 | 원래 worker만 지정, start.lock/run.lock 중복 실행 거부 |
| 4.<br>준비 | 같은 캐시 검증 후 실효 prepare 실행 | 새 수신 없이 source_frozen에서 prepared.json으로 연결 |
| 5.<br>결과 확인 | 이전 failed 기록·resume_of·새 작업과 final 대응 | 원본·실효 계약과 manifest SHA 모두 일치 |
| 6.<br>보고서 | 12차 기본 검증 다음 validate_recovery 수행 | Word·동일 원고 PDF 두 파일만 새 폴더, 기존 미완료 본 보존 |

공식 대응의 기준 집계는 과거 1,999·5차 3,839·교집합 642·합집합 5,196 ID입니다.

이는 표본별 바이트 동일성의 증거가 아닙니다.

과거 JPEG는 재인코딩되고 최대 2,048 축소됐으므로 과거 SHA와 새 원본 SHA를 구분합니다.

원래 준비 계약에는 원본 코드 SHA를 남기고 recovery13.json에 실효 코드·ID resolver·입력·작업 계보를 고정합니다. prepare_bound는 준비 뒤 입력 해시를 다시 확인하고 prepared.json에 data_manifest와 base 계약의 SHA를 묶으며 _prepared _binding이 이를 다시 읽습니다.

기존 root가 13차인 검사 방법은 공통 명령 란에 있습니다.

시작·worker에는 --plan과 --expected-canonical이 모두 필요하고 일시 정지된 작업을 조회만으로 시작하지 않습니다.

동일 두 후보의 최대 60·45 epoch·각 6시간 계획과 원래 분할·평가를 유지하며 다른 GPU 작업은 종료하지 않습니다.

캐시 부재나 손상은 새 수신으로 우회하지 않습니다.

기록된 Windows unittest는 43개 중 Linux 1개 건너뜀, Docker는 43개 통과입니다.

회귀는 잘못된 ID·추가 AST/텍스트 차이·캐시 변조·중복 기동·실패 상태·계보·보고서 연결을 확인했고 보고서 입력은 합성 자료입니다.

GPU 학습 완료와 최종 성능은 이 검사로 판정할 수 없고 90% 달성을 보장하지 않습니다. 13차 복구는 과거 기록을 DMF 롤 백하는 기능이 아닙니다.

### 현재 공개 사본의 원본 대조
