## 결과 영상 경로 수리 1

부모가 실제 브라우저와 HTTP 요청에서 기존 탐지 결과 두 개의 재생 실패를 확인했습니다. 5차 작업 JSON의 /workspace/2026 경로가 8차 상태에 그대로 노출되어 Windows 파일 경계 검사가 400으로 차단한 것이 원인입니다. pipeline.py의 기존 탐지 작업 표시 데이터에 원래 legacy.local_paths 변환을 적용했습니다. tests/test_adapter.py에는 컨테이너→Windows 상태 변환과 실제 HTTP 핸들러의 임시 결과 파일 Range 206·경계 밖 400 검사를 추가했습니다. ROUTING-LESSONS.md에 실패와 수리 근거를 보존했습니다. 인증·파일 경계·원본 5차·7차·학습 작업은 변경하지 않았습니다. 기존 21개 첫 통과 기록은 실제 미디어 경로 누락을 발견하지 못한 검사 범위의 한계로 보존합니다. 수리 누적 1회, 입력 보정 누적 2회이며 별도 독립 검증과 부모의 제품 서버 재시작·실제 영상 재확인이 필요합니다.

수리 1 구현자 실검사: 같은 8차 cwd에서 unittest discover 23개 통과, verify_sources.py 배포 15파일·원본 의존 14개 통과, Node --check 통과로 각 종료 코드 0입니다. 실데이터 상태 조회의 기존 두 결과 경로는 D:/2026 아래 기존 5차 results 파일로 변환됐고 두 파일의 존재를 직접 확인했습니다. HTTP Range 206 검사는 임시 결과 파일에 대한 실제 요청이며, 제품 서버의 보존 영상 재생 재확인은 부모의 재시작·UI 검사에서 별도로 수행합니다.

추가 확정 기준: 현재 클린뷰를 이후 차수에도 유지하도록 docs/대시보드기준.md에 기록했습니다. 제품 배치와 실행 코드는 변경하지 않았습니다. 비교 문서는 CRLF 변환이 있던 이전본을 비공개 증거에 보존하고 원본 바이트의 LF 경계와 CR을 그대로 사용해 재생성했습니다. 7차 기준은 지정 Git 커밋의 blob을 직접 읽고, 5차 화면 비교는 설치 원본의 공통 화면 코드 파일을 직접 읽습니다. 공개 패치에 포함된 원본 CR은 정확한 비교 자료의 일부이므로 제품 소스의 불필요한 공백 오류와 구분합니다.
