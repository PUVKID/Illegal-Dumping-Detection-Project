# 11차 복구 설계

## 요구와 확인된 원인

사용자가 오류를 확인하고 이어서 진행하라고 요청했습니다. 공식 원자료의 현재 부분 파일과 원장·기존 모델·평가·준비 계약을 보존해야 합니다. 7차 실패는 다운로드 범위의 40초 경과 검사에서 발생했으며 최대 6회 재시도가 소진됐습니다. 경과에는 연결·수신뿐 아니라 디스크 여유 확인, 원장 atomic 교체와 여러 작업 상태 저장이 포함됩니다. 실제 `read1`은 최대 요청 길이보다 작은 본문을 여러 번 반환합니다. 과거 네트워크와 상태 쓰기 각각의 시간 비율은 남은 자료만으로 확정하지 않았습니다.

7차 준비 계약은 준비 코드 전체 해시를 고정합니다. 따라서 그 파일을 고치거나 계약을 현재 해시로 갱신하는 대신 별도 실행기에서 수신만 보완합니다. `original-baseline.json`은 변경 전 7차 제품 16개를 고정하며, 운영 이력과 실행 자료를 제품 소스로 합산하지 않습니다.

## 단일 작업과 기존 계약

시작은 기존 작업자의 시작 잠금·작업 정리·실행 잠금을 거칩니다. 실제 명령에는 고정 7차 작업자 경로와 작업 ID가 들어가며, 실제 진입점은 11차라는 사실과 해시·인자를 작업과 복구 영수증에 명시합니다. 프로세스 생존 판정은 기존 작업자와 같은 계약을 사용하며 서버 신원 인증으로 확대하지 않습니다.

실행 중에는 원래 `worker.execute`가 전체 실행 잠금과 실패 상태·로그를 관리합니다. 그 프로세스의 `train_pipeline.run`에만 수신 후 원래 함수를 호출하는 연결을 두고 종료 시 복원합니다. 파일의 구현·준비·분할·평가 함수와 불변 계약은 변경하지 않습니다. 준비 계약 전체와 공식 원자료 명세를 먼저 대조하고, 기존 사전 전송 영수증도 수신 전에 정확히 한 번 합산·재검사합니다.

수신기는 같은 Linux 파일 잠금, `.part`와 `.part.json`, 원장을 사용합니다. 64KiB부터 시작해 10초 미만 성공이면 증가, 20초 이상이나 경과에 따른 자발적 분할이면 감소하며 상한은 기존 4MiB입니다. 각 범위에는 40초 경과 확인과 소켓 40초 timeout을 유지합니다. 운영체제의 블로킹 I/O를 정확히 40초에 강제 종료한다는 보장은 아닙니다. 네트워크·EOF·부분 본문의 실제 오류는 진행이 있어도 제한된 재시도에 포함합니다. 실제 진행을 보존한 자발적 경과 분할만 다음 범위로 나눕니다.

수신 본문은 원장에 먼저 계상하고 디스크에 씁니다. 원장·상태·디스크 오류는 통신 재시도로 처리하지 않습니다. 요청 전 불확실 표식을 영속하며 실제 저장 위치와 원장의 반영을 확인한 뒤에만 해제합니다. 표식이 남으면 다음 11차 실행은 감사 필요 오류로 멈춥니다. 운영체제 전체 쓰기 실패까지 복구하거나 표식을 모르는 원래 7차 CLI의 수동 실행까지 차단한다고 주장하지 않습니다. 그런 경계에서는 원장·부분 파일·실패 작업을 직접 감사해야 합니다.

## 성공 조건과 검사

- 공식 범위 응답, 실제 저장 위치, 부분 본문과 실패 전송 계상, 최대 6회 통신 재시도, 제한된 Retry-After가 일치해야 합니다.
- 진행하는 느린 범위는 부분 파일을 보존해 나누고, 무진행·잘못된 범위·4xx·손상·예산·디스크·원장·통지 오류는 숨기지 않습니다.
- 완료 파일의 공식 크기·MD5와 전체 SHA-256을 검사하고 기존 verified 영수증과 호환되어야 합니다. ZIP CRC와 데이터 분할은 원래 준비 함수가 후속 검사합니다.
- 중복 실행·기동 실패·자식 종료·위조 경로·계약 오염을 회귀 검사하고 원래 함수를 성공 전에 호출하지 않아야 합니다.
- 전체 11차 제품 7개의 엄격 UTF-8·구문과 외부 고정 canonical 해시, 7차 원본 16개를 검사합니다. 비공개 운영 evidence와 실행 work는 동결 제품과 구분합니다.

TDD의 통제 실패와 구현·검증 결과는 비공개 증거에 보존합니다. 테스트 통과는 실제 대용량 수신·GPU 학습 완료나 모든 오류 부재를 보장하지 않습니다. 실제 시작은 독립 검증과 부모 조율 뒤 수행합니다.
